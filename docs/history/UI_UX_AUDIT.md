## Intro: приоритетные находки

### 1. P1 — принудительные остановки после каждого символа

**Место:** [assets/ambient.js:107](../../assets/ambient.js#L107), строки 117–127. Подтверждено алгоритмом.

`letterMs = 225`; каждый символ получает отдельный smoothstep. Деление локального прогресса на `0.9` завершает движение за 202,5 мс, оставляя 22,5 мс неподвижности. Скорость обнуляется на каждой границе. Пробел также занимает 225 мс, а широкие и узкие буквы раскрываются за одинаковое время. Получается серия импульсов, а не непрерывная волна. Это не проблема `linear`: текущая функция уже нелинейная, но применяется заново к каждому символу.

**Минимальный фикс:** один нормализованный прогресс на всю строку с одной плавной кривой. Убрать паузы и зависимость длительности от количества символов. Если нужно сохранить форму раскрытия, интерполировать границу непрерывно, без остановок на пробелах. Это локальная замена вычисления прогресса.

### 2. P1 — обновление градиентной маски в каждом кадре

**Место:** [assets/ambient.js:120](../../assets/ambient.js#L120), строки 128–137; [styles.css:22](../../styles.css#L22). По коду; стоимость Paint/Raster не измерена.

rAF каждый кадр создаёт строку градиента и записывает `maskImage` и `webkitMaskImage`. Это не обычное перемещение готового слоя: меняется изображение маски. Одновременно первые 900 мс изменяется blur. Внутри `draw()` нет сетевых вызовов, DOM-обходов или чтений геометрии; утверждение о layout thrashing в каждом кадре было бы неверным. Проблемное место — обновление маски и возможная растеризация, а не тяжёлая арифметика JS.

**Минимальный фикс:** если допустима небольшая корректировка эффекта — раскрывать всю надпись через opacity и небольшой transform, убрать анимируемые mask/blur. Если направленное раскрытие обязательно — отдельный перемещаемый слой с неизменной маской; проверить его композитинг в DevTools. Одно лишь добавление `will-change` не делает обновляемый градиент бесплатным. [Рекомендации Chrome по анимациям](https://web.dev/articles/animations-guide).

### 3. P2 — резкое снятие маски в конце, масштаб feather не связан со шрифтом

**Место:** [assets/ambient.js:128](../../assets/ambient.js#L128), строки 128–138; [styles.css:21](../../styles.css#L21). По коду.

Непрозрачная часть заканчивается в `edge - 24px`, затем маска сразу заменяется на `none`. Полоса последних пикселей может ещё оставаться полупрозрачной: правый padding текста — только `0.15em`. При размере шрифта 36px это 5,4px, при 102,4px — 15,36px. Feather 36px занимает очень разную долю текста на мобильном и desktop. Это создаёт потенциальное внезапное проявление окончания строки.

**Минимальный фикс при сохранении маски:** вывести её непрозрачную границу за правый край текста до удаления; ширину feather задать относительно размера шрифта. Не снимать маску, пока она ещё изменяет видимые пиксели.

### 4. P1 — таймаут шрифта разрешает смену геометрии посреди intro

**Место:** [assets/ambient.js:96](../../assets/ambient.js#L96), строки 107–115 и 167–174; [styles.css:1](../../styles.css#L1), строки 1–2. Риск медленной/неудачной загрузки, в этой сессии не воспроизведён.

`Promise.race` ждёт Pencerio максимум 1500 мс, а `font-display: swap` допускает позднюю подмену. После таймаута измеряются границы fallback-текста, затем Pencerio может изменить ширину и центрирование строки. Массив `edges` остаётся старым. Загрузка Telma для навигации отдельно не синхронизируется с появлением страницы.

**Минимальный фикс:** если Pencerio не готов к дедлайну — пропустить intro либо зафиксировать fallback на весь показ. Не позволять шрифту меняться после измерения. Подготовить скрытый текст и измерить его до запуска; класс движения добавлять после измерений. Preload обоих шрифтов уже есть, дублировать его не нужно.

### 5. P2 — несколько конкурирующих фаз и двойное затухание карточки

**Место:** [styles.css:15](../../styles.css#L15), строки 18–30, 32; [assets/ambient.js:144](../../assets/ambient.js#L144), строки 144–177. По коду.

Надпись получает opacity 500 мс, blur 900 мс, transform 1200 мс; раскрытие длится 2475–3375 мс; только потом появляется декоративная линия за 450 мс; через 680 мс начинается выход. Страница одновременно увеличивает opacity, пока закрывающий её intro уменьшает opacity. При одинаковом прогрессе `p` вклад страницы примерно `p²`: в середине перехода при `p=0.5` она видна лишь на 25%. Карточка воспринимается как запоздалая. При этом сама карточка и её тень находятся под общим opacity `.page` — отдельной задержки тени в коде нет.

**Минимальный фикс:** подготовить полностью непрозрачную страницу под intro и плавно убрать только overlay. Сократить число фаз текста; декоративную линию либо включить в общую фазу, либо убрать. Она не отражает загрузку и не должна выглядеть как прогресс-бар. Согласовать время через несколько CSS-переменных для появления, удержания и выхода.

### 6. P2 — safety timeout может оборвать выход; завершение привязано к числу 720

**Место:** [assets/ambient.js:31](../../assets/ambient.js#L31), строки 31–40, 150–156. По коду, сценарий медленного старта.

Семисекундный safety отсчитывается ещё из head, а нормальная последовательность включает ожидание DOM, до 1500 мс ожидания шрифта, 3375 мс длинного приветствия, 680 мс удержания и 720 мс выхода. Для `good afternoon.` после font timeout остаётся примерно 725 мс на всё остальное до аварийного завершения. Safety скрывает overlay напрямую и не отменяет текущий rAF. Обычный выход дублирует CSS duration числом в JS, поэтому изменение CSS легко рассинхронизирует завершение.

**Минимальный фикс:** единая идемпотентная функция очистки, отменяющая rAF и таймеры. Нормальное завершение — по `transitionend` конкретного opacity с запасным таймаутом; при reduced motion завершать сразу. Аварийный предел учитывать относительно реального запуска фаз, сохранив отдельную защиту от зависшего старта.

### 7. P2 — intro повторно блокирует доступ, включая прямые ссылки

**Место:** [assets/ambient.js:26](../../assets/ambient.js#L26), строки 26–29, 87–91. По коду; повторный показ при полной навигации наблюдался.

Условия учитывают iframe, reduced motion и `manage=1`, но не повторное посещение или `#post/...`. Без ожидания шрифта сам цикл занимает около 3,875–4,775 секунды; всё это время основной интерфейс inert. Для небольшого архива это ощутимая задержка доступа к содержимому.

**Минимальный фикс:** показывать один раз за сессию и пропускать на прямой ссылке на запись; сохранить Escape и skip. Это продуктовая рекомендация, а не требование ускорять все переходы одинаково.

## Интерфейс, состояния и доступность

### 8. P1 — `hidden` не скрывает owner actions и ссылку внутри открытого поста

**Место:** [styles.css:74](../../styles.css#L74), строки 74, 80; [site.js:173](../../site.js#L173), строки 173–182; [index.html:66](../../index.html#L66), строки 66–68.

Авторские `display:inline-block` у `.detail a` и `display:flex` у `.owner-actions` переопределяют обычный HTML `hidden`. На живой странице computed style подтверждает эти display при `hidden=true`; пока скрыт родитель detail, сами элементы не видны. При открытии поста посетитель получит неработающие edit/delete. После поста со ссылкой открытие поста без ссылки также может оставить старое имя хоста: `href` удаляется, `textContent` не очищается. Никакой обход прав этим не доказан — обработчики дополнительно проверяют `canPublish`.

**Минимальный фикс:** явные `.owner-actions[hidden], .detail a[hidden] { display:none; }`; в ветке отсутствующей ссылки также очистить её текст. Это тот же подход, который уже применён к `.panel[hidden]`. [Поведение hidden в MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/hidden).

### 9. P1 — часы перекрывают карточку на коротком мобильном viewport

**Место:** [styles.css:32](../../styles.css#L32), строки 32–39, 109–110. Воспроизведено.

На 320×480 карточка: `x=16, y=72, w=288, h=336`, низ 408px. Часы: `x=218.53, y=383.06, w=85.47, h=77.75`. Пересечение — примерно 85×25px. Часы имеют больший z-index. Текущее скрытие срабатывает лишь при высоте до 448px и не закрывает диапазон чуть выше. На 375×812 и 640×360 этого пересечения в измеренных bounds нет.

**Минимальный фикс:** для узкого viewport при недостаточной высоте размещать часы ниже карточки в потоке либо резервировать место под них. Если выбран вариант скрытия — порог вычислить с учётом высоты карточки и часов, а не только landscape. Проверить также увеличение текста и экранную клавиатуру.

### 10. P2 — слишком маленькие текстовые цели нажатия

**Место:** [styles.css:48](../../styles.css#L48), строки 48, 76, 78, 87, 107. Частично измерено.

В owner access кнопки cancel/send link имеют высоту 15,59px и нулевые padding. Так же устроены back, clear, edit/delete, save draft/publish. Поиск имеет текст 12,16px и line-height около 15,2px без padding. Плюс — 24×24px; табы — примерно 43×32px; hide time — около 30,4px по высоте. Именно `.plain` и поиск наиболее проблемны для пальца; у остальных есть запас для улучшения, но это не одинаковая тяжесть.

**Минимальный фикс:** увеличить реальную область нажатия текстовых кнопок и поля, сохранив небольшой визуальный текст; для touch целиться в 40–44px, для компактных desktop-контролов обеспечить хотя бы удобный минимум и интервалы. Не объявлять автоматически каждую цель меньше 24px нарушением WCAG: стандарт допускает исключение по расстоянию. [W3C: target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum).

### 11. P2 — внешний focus-ring обрезается у границ прокручиваемого списка

**Место:** [styles.css:12](../../styles.css#L12), строки 56, 59–60. По коду; в production нет строк постов для визуального воспроизведения.

Кнопка поста занимает всю ширину и начинается у левого края scroller. Глобальный outline вынесен наружу на 3px плюс собственные 2px, а `.post-list` имеет `overflow-y:auto`. Внешняя часть обводки у края будет отсечена. Подчёркивание на focus остаётся, поэтому речь о неполном кольце, а не о полном отсутствии фокуса. У пустой tabpanel браузерная обводка в проверке видна.

**Минимальный фикс:** для кнопок внутри scroller использовать внутренний outline/box-shadow либо небольшой внутренний отступ scroller с компенсацией геометрии. Проверить первую и последнюю строку и ссылку в detail.

### 12. P2 — отсутствующая запись бесшумно превращается в раздел work

**Место:** [site.js:217](../../site.js#L217), строки 217–230. Воспроизведено на `#post/audit-missing-post`.

После успешной загрузки неизвестный ID приводит к замене адреса на `#work`. Пользователь не узнаёт, что ссылка не найдена или запись больше недоступна. Красивый HTTP 404 этого сценария не покрывает: это hash-маршрут внутри index.

**Минимальный фикс:** отдельное состояние «this post isn't available» с возвратом к списку; не различать для посетителя удалённую и приватную запись. Сохранить ошибочный маршрут до осознанного возврата пользователя.

### 13. P1 — закрытие редактора теряет несохранённый текст

**Место:** [site.js:337](../../site.js#L337), строки 339, 412–417. По коду.

Discard закрывает диалог сразу, Escape также разрешён, если запрос не выполняется. Следующее открытие вызывает `form.reset()`. Даже большой набранный текст теряется без подтверждения. В проекте уже есть confirm dialog, но для грязного редактора он не используется.

**Минимальный фикс:** сохранить начальный снимок значений и сравнивать перед закрытием; при изменениях спросить подтверждение через существующий диалог. Чистый редактор закрывать сразу. Для подтверждения отмены настроить собственную подпись отменяющей кнопки, а не оставлять «keep post» из удаления.

### 14. P1 — во время сохранения разрешено редактировать уже отправленный текст

**Место:** [site.js:424](../../site.js#L424), строки 424–431, 441–461. По коду.

Payload фиксируется перед запросом. Отключаются только три кнопки; input, textarea и select остаются редактируемыми. Пользователь может продолжить писать, после чего успешный ответ закроет форму, хотя новые изменения не попали в payload. Это потеря текста, не просто отсутствие спиннера.

**Минимальный фикс:** на время запроса заморозить поля формы и показать «saving…»/`aria-busy`; обязательно восстановить доступность при ошибке. Либо сохранить возможность ввода, но сравнивать текущий снимок с отправленным и не закрывать форму при расхождении — первый вариант проще.

### 15. P2 — удаление не имеет состояния выполнения

**Место:** [site.js:473](../../site.js#L473), строки 475–491. По коду.

После подтверждения запрос выполняется при прежнем виде страницы; нет disabled/busy. Можно повторно нажать delete или перейти к редактированию до ответа. Пользователю непонятно, принят ли запрос.

**Минимальный фикс:** фиксировать ID удаляемой записи, блокировать соответствующие owner actions до ответа, показывать короткий статус. При ошибке восстановить действия и оставить существующий alert.

### 16. P2 — загрузка, пустой результат и успешная отправка не объявляются как статусы

**Место:** [site.js:82](../../site.js#L82), строки 82–128, 550; [index.html:51](../../index.html#L51), строки 51–59, 106. По коду.

Динамические сообщения создаются обычными `<p>`, без live region; при поиске нет объявления количества/отсутствия результатов. Текст «check your inbox» также заменяется в обычном параграфе. Ошибки форм используют `role=alert` — это уже правильно, но успешные и фоновые изменения не покрыты.

**Минимальный фикс:** один заранее существующий `role=status`/`aria-live=polite`, обновляемый завершённым результатом; `aria-busy` на области загрузки. Не делать весь список или тикающие каждую секунду часы live region.

### 17. P2 — пустая карточка до исполнения приложения при медленном CDN

**Место:** [index.html:57](../../index.html#L57), строки 57–59, 121–122; [site.js:574](../../site.js#L574), строки 574–581. Риск медленной загрузки, не измерен.

Исходный HTML содержит пустые post-list. `loading...` появляется только после запуска site.js, а этот defer-скрипт стоит после внешнего SDK. Пока CDN не завершил загрузку или не сообщил ошибку, после выхода intro можно увидеть просто пустую карточку. Обработка окончательного отсутствия SDK есть; не обработан период ожидания его загрузки.

**Минимальный фикс:** добавить начальное loading-состояние непосредственно в HTML, которое существующий render заменит. Для отключённого JS — короткое noscript-сообщение. Не нужен новый загрузчик или перестройка приложения.

### 18. P2 — место поиска появляется только после данных и сдвигает содержимое

**Место:** [site.js:70](../../site.js#L70), строки 70–74, 112; [styles.css:46](../../styles.css#L46), строки 46–53. По коду; численный CLS не измерен.

После прихода первых постов `search-region` перестаёт быть hidden и отнимает высоту у контента. На медленной загрузке это происходит уже после intro; при reduced motion — без прикрытия. Появление clear дополнительно меняет ширину input. Шрифт Telma с `swap` может отдельно изменить надписи табов, но их минимальные размеры снижают риск сдвига. Нельзя приписывать сдвиг карточки тикающим часам: они fixed, а цифры tabular.

**Минимальный фикс:** резервировать место поиска на время начальной загрузки либо показывать стабильную строку поиска для всех состояний. Сохранять отдельную ячейку clear при пустом запросе. Не связывать завершение intro с сетевым ответом.

### 19. P2 — поиск пересоздаёт весь DOM всех трёх списков на каждый символ

**Место:** [site.js:51](../../site.js#L51), строки 51–60, 103–151, 390–394. Риск при наполнении, не текущая измеренная просадка.

На каждый input заново нормализуются полные тексты, фильтруются категории, удаляются все строки, создаются кнопки и обработчики, включая скрытые панели. Загрузка получает полные body всех постов. На маленьком пустом портфолио это незаметно; с длинными заметками это потенциальная задержка ввода. Частичная перестройка также не сохраняет явно положение чтения списка.

**Минимальный фикс:** при загрузке подготовить строку поиска для каждого поста; нормализовать запрос один раз, обновлять видимый список, использовать небольшой debounce для ввода. Явно определить scroll policy: новый запрос начинает результаты сверху, возврат из detail сохраняет позицию. Не нужен фреймворк, виртуализация или новый backend.

### 20. P2 — фоновое обновление может неожиданно забрать фокус

**Место:** [site.js:188](../../site.js#L188), строки 188, 223–224, 261–262, 591–599. По коду.

Каждый refreshPosts вызывает restoreLocation; открытый пост снова вызывает showPost, а тот безусловно делает `detail.focus()`. Обновление авторизации также приводит к refreshPosts. Фокус может уйти со ссылки или кнопки, даже если пользователь никуда не переходил. Сохранение scroll через `resetScroll=false` не предотвращает перенос фокуса.

**Минимальный фикс:** разделить флаг переноса фокуса и флаг сброса прокрутки. Фокусировать detail только при осознанном открытии записи или начальном переходе, не при фоновой синхронизации.

### 21. P2 — старая ошибка формы входа остаётся при успешной повторной попытке

**Место:** [site.js:509](../../site.js#L509), строки 520–550. По коду, отправка письма не выполнялась.

Ошибка невалидного email показывает `#auth-error`. После исправления адреса обработчик не скрывает прежний alert ни перед запросом, ни в успешной ветке. Можно получить одновременно «enter a valid email address» и «check your inbox». Во время самого запроса подпись кнопки также остаётся «send link».

**Минимальный фикс:** сбрасывать предыдущую ошибку после успешной локальной валидации, до запроса; показывать «sending…» и затем согласованное состояние успеха. Связать сообщение с полем через `aria-describedby`, при невалидном значении ставить `aria-invalid`.

### 22. P3 — hover есть, feedback на нажатие почти отсутствует

**Место:** [styles.css:28](../../styles.css#L28), строки 28–29, 35–44, 76–79, 95. По коду.

У табов, plain-кнопок, плюса и часов есть hover; общий focus-visible есть. Но явных `:active` нет. `.plain:disabled` меняет opacity и cursor, однако hover всё ещё может менять цвет. У плюса вращение на 90° почти не меняет симметричный знак в конечной точке; его основной feedback — только само движение. Отсутствие disabled у табов/часов не дефект: приложение их не отключает.

**Минимальный фикс:** общий короткий pressed-state без изменения layout; hover ограничить `:not(:disabled)`. Для плюса предпочтительнее небольшое изменение фона/цвета или масштаба, сохранив reduced motion. Для полей не нужно механически добавлять все четыре состояния, если у них нет соответствующего сценария.

### 23. P3 — система размеров существует частично и избыточно дробится

**Место:** [styles.css:4](../../styles.css#L4), строки 20, 33–41, 46–53, 61–76, 87–94, 106–107. По коду и визуально.

Есть пять spacing-токенов, но рядом используются 1.38, 1.08, 0.78, 0.55, 0.42, 0.62, 0.8, 0.95rem и другие независимые значения. Шрифты повторяют близкие размеры 0.7/0.72/0.75/0.76/0.78/0.81/0.82rem. Табам достаётся декоративная Telma при 12,96px; подписи часов — 10,08px. Интерфейс аккуратен, но микроразмеры затрудняют чтение и поддержку согласованности.

**Минимальный фикс:** объединить близкие значения в несколько ролей: подпись, контрол, основной текст, заголовок; унифицировать интервалы форм и контента. Оставить оптические поправки для рукописного шрифта. Обязательная 8px-сетка нигде не заявлена, и сам факт дробного rem не является багом.

## Текстуры, тени, DPI и motion: что доказано и что нет

- **SVG не гарантирует резкость автоматически.** [paper-ground.svg:3](../../assets/images/paper-ground.svg#L3) и [paper-sheet.svg:3](../../assets/images/paper-sheet.svg#L3) содержат turbulence, displacement и `feGaussianBlur stdDeviation=10`. Размытость заложена в изображениях. На проверенном DPR 1 фон выглядит как мягкие широкие складки, карточка заметно ровнее; это дизайн-наблюдение, не доказательство испорченной Retina-растеризации. Минимальная коррекция, если нужна именно бумажная фактура: отдельно настроить blur/opacity складок и едва заметное зерно, не увеличивать хаотично контраст всей поверхности.
- **`cover` меняет масштаб и обрезку рисунка.** [styles.css:10](../../styles.css#L10), строка 39. На разных соотношениях сторон меняется видимая часть складок; на узком экране карточка 288×336 вместо квадрата. Если художественное требование — одинаковый масштаб фактуры, минимально разделить крупные складки и мелкую повторяемую фактуру. Пока такого требования нет, это не функциональная поломка.
- **Clip-path и тень устроены правильно по слоям.** [styles.css:38](../../styles.css#L38), строка 39: тень на внешнем `.paper-lift`, обрезка — на `.board`. На проверенных экранах нет доказанного отрезания тени самим clip-path. Субпиксельные неровности контура при 288–336px очень малы; внешний край и inset 1px могут менять антиалиасинг на разных zoom. Проверить DPR 2/3 и 125/150/200% до изменения геометрии.
- **Текстуры не анимируются каждый кадр.** Не следует объявлять turbulence постоянным источником 60 перерисовок в секунду. Риск — начальная растеризация, изменение размера и инвалидирование слоя. Две drop-shadow увеличивают потенциальную стоимость этой работы, но без trace их нельзя назвать измеренной причиной рывков intro.
- **Нет анимирования width/height/top/left.** Габариты карточки и позиции часов статичны или переключаются media query. `panel-in` использует opacity/translateY и длится 140 мс. Layout-чтения границ букв выполняются один раз перед rAF-циклом, не на каждом кадре. Класс `.is-playing` добавляется перед первым чтением геометрии — здесь возможен стартовый синхронный style/layout flush, но не доказан длинный кадр.
- **Нет will-change/translateZ(0).** Само отсутствие не дефект. Добавлять временный `will-change: transform, opacity` имеет смысл только для реально анимируемых элементов и до запуска, затем снимать. Не раздавать его всем текстурам и всей странице: слои расходуют память, а маску этот hint не исправит. [MDN: will-change](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change).
- **Тайминги частично согласованы.** Большинство изменения цвета — 180 мс ease, underline/plus — 120 мс ease, панели — 140 мс ease-out. Это разумное разделение типов действий; не нужно сводить всё к одной скорости. Главный выброс — intro с 450/500/680/720/900/1200 мс и побуквенным шагом 225 мс. `ease` уже является cubic-bezier, а не linear.
- **Часы не должны вызывать CLS каждую секунду.** Они fixed, используют tabular-nums и стабильный формат HH:mm:ss. Hide/show переключает display внутренних элементов мгновенно; это отдельное сознательное действие, не доказанный CLS. Появление изначально пустого `<time>` не двигает карточку, но геометрию самого виджета стоит проверять отдельно.
- **Фокус базово реализован.** Табы используют roving tabindex, ArrowLeft/Right/Home/End; стрелка вправо в живой проверке переключила активный таб и фокус. Общий ring виден, табпанель тоже получает видимую браузерную обводку. Dialog использует showModal и фокусирует email/title. Проблемы точечные: обрезка кольца внутри scroller и повторный программный перенос фокуса.
- **Reduced motion предусмотрен.** Intro пропускается при исходном reduce, transitions и panel animation отключаются. При изменении настройки посреди intro вызывается finishIntro, но inert сохраняется до JS-таймаута 720 мс — это дополнительный аргумент для исправления общего завершения из пункта 6.
- **Пустые состояния не ограничиваются «nothing published yet».** Есть loading, no search matches, load error + retry, unconfigured connection, ошибки форм, удаление с alert и отдельный 404. Пробел — недоступный hash-пост, старт до исполнения JS и объявления состояний для assistive technology. Тексты пустых work/notes/about одинаковые; при желании можно сделать их смыслово различимыми без новых компонентов.

## Как закрыть недостающую Performance-проверку

В Chrome DevTools Performance записать полную загрузку и intro на том же commit: минимум холодный cache и повторную загрузку; отдельно 320×480 и DPR 2. Указать CPU/network throttling и частоту экрана. Сравнить ту же сцену с временно отключённой маской/blur в DevTools, не меняя production.

В trace отметить: запуск ambient; выполнение initialize; готовность/таймаут Pencerio; первое getBoundingClientRect; rAF draw; появление progress; finishIntro; снятие overlay. Искомые связи: стартовый Layout — `ambient.js:96–115`; повторные Style/Paint/Raster — записи маски `130–132`; blur — `styles.css:22`; декодирование/растеризация SVG — `styles.css:10,38–39`; синхронный renderPosts — `site.js:103–151`.

Отчёт измерения должен содержать FPS/интервалы кадров именно на интервале intro, p95 и максимальный интервал, число пропущенных кадров относительно частоты дисплея, конкретные длинные задачи и их стек, CLS и список layout-shift entries. Средний FPS по всей загрузке или один скриншот не подходят. Если видимое подёргивание остаётся при ровных кадрах, пункт 1 уже объясняет причину: это остановки траектории.

## Порядок точечных исправлений

Сначала 1–6 (алгоритм и завершение intro), 8 (hidden), 9 (перекрытие), 13–14 (сохранность текста). Затем 10–12 и 15–21 (управление, фокус, состояния). В последнюю очередь 22–23 и художественная доводка фактуры после проверки DPI. Ни один из этих шагов не требует смены архитектуры или зависимостей.
